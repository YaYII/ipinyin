# 项目④：中文地区用语转换 zh-CN ↔ zh-TW（词表基线）

大陆/台湾用语差异（软件→軟體、信息→資訊、视频→影片）与「普→粤」是同构问题：
字面映射之外，难的是**短语级用词替换 + 语境判断**。本目录先做词表基线——
最长匹配双向转换 + 歧义报告；neural 版与实证守卫留待下一轮。

与 OpenCC 的关系：映射数据全部来自 OpenCC 社区词典（Apache-2.0，人工审校），
本目录的贡献是把它们组装成**可评测、可报告歧义**的双向管线，并给出地区版
的「守卫」证据清单。

## 用法

```bash

$PY fetch_opencc.py                      # 拉数据 → data/opencc_pairs.json

#   他把文件放在U盘里。
$PY convert.py --report                  # 歧义报告（守卫清单）
$PY eval.py                              # held-out 评测 + 语境测试句
$PY -m pytest test_convert.py -q         # 17 个用例
```

## 管线

复刻 OpenCC 官方链（s2twp / tw2sp 配置），每级内部**短语最长匹配 > 单字映射 >
原样保留**；同级多表冲突时地区用词表胜出（对齐官方 `short_circuit` 语义）：

- `cn→tw`：`[STPhrases + STCharacters]` → `[TWPhrases + TWVariantsPhrases + TWVariants]`
- `tw→cn`：`[TWVariantsRevPhrases + TWPhrasesRev]` → `[TSPhrases + TSCharacters]`

两级设计是刻意的：第一级只管简繁，第二级只管用词。`程序正義→程序正義` 这类
identity 词条是最长的匹配，天然挡住 `程序→程式` 的波及——OpenCC 自己的守卫。

## 实测数字

held-out 切分（90/10，seed=0；测试对的词条从短语表移除、单字映射保留）：

| 方向 | 整词命中率 | 纯单字映射 | 词级对命中率 | 训练集上限 |
|---|---|---|---|---|
| cn→tw（3920 测试对） | **83.4%** | 76.8% | **32.0%**（291/910） | 99.9% |
| tw→cn（117 测试对） | **19.7%** | 12.0% | **9.7%**（10/103） | 99.2% |

解读：
- 词级对 = 单字映射拼不出、必须靠短语表的词对。held-out 上 cn→tw 仍有 32%
  命中，靠的是组合泛化（测试对「软件开发」被训练集的「软件→軟體」拼出来），
  不是泄题；tw→cn 只有 9.7%，因为反向词表几乎没有可复用的长词条。
- 训练集上限 ≈100% 说明合成词对与转换器口径一致（曾修掉一个派生口径 bug）。
- 这两个数字就是 neural 版要打的靶子：把 held-out 词级命中率从 32%/10%
  提上去，同时不破坏下表的守卫句。

## 歧义报告（「守卫」的地区版雏形）

`convert.py --report` 输出三类证据：

1. **一对多映射**：OpenCC 行内多值（首选取胜）。ts_chars 997、st_chars 276、
   st_phrases 114、tw_phrases_rev 49、tw_phrases 44…。例：
   `視頻 → 影片 | 視訊`、`代碼 → 程式碼 | 代碼`、`宏 → 宏 | 巨集`。
2. **长度冲突**：长短语覆盖短信语后，覆盖段的实际转换 ≠ 短语自身映射。
   cn2tw#L1 1425 条 / cn2tw#L2 67 条 / tw2cn#L1 76 条 / tw2cn#L2 2 条，
   一致覆盖另计（26417 等）。有用的例子：`司法程序→司法程序` 覆盖
   `程序→程式`（需要的守卫）；`大數據→大數據` 覆盖 `數據→資料`（隐患）。
3. **往返不对称**：cn→tw 后 tw→cn 回不到原词，上限 200 例。例：
   `B超 → 超音波 → 超声波`、`个人资料 → 個人資料 → 个人数据`
   （一对多收敛的反向只能选一个赢家；其中一部分恰恰是想要的地区归一）。

## 语境依赖测试句与失败模式

`eval.py` 内置 16 句人工标注（9 句 baseline 应当全过、7 句已知盲区应当全暴露），
实测 9/16：**baseline 9/9 通过，盲区 0/7 通过**——词表基线的边界被精确定位：

| 模式 | 例句 | 期望 | 实得 | 根因 |
|---|---|---|---|---|
| 过度转换 | 把文件打印出来。 | 把文件列印出來。 | 把**檔案**列印出來。 | 文件（纸质义）被一律转成 檔案（计算机义） |
| 过度转换 | 投票程序很简单。 | 投票程序很簡單。 | 投票**程式**很簡單。 | 程序（流程义）→程式；identity 守卫只保固定搭配 |
| 漏转 | 这款手机质量很好。 | 這款手機**品質**很好。 | 質量未动 | 质量→品質 不在词表（OpenCC 未收） |
| 组合词缺失 | 智能手机改变了生活。 | **智慧型**手機。 | 智慧手機 | 逐词替换拼不出 智慧型 构词 |
| 漏转 | 地铁出口在哪里？ | **捷運**出口。 | 地鐵 | 同概念不同词，非字面差异 |
| 反向漏转 | 這個軟體的品質不錯。 | 这个软件的**质量**不错。 | 品质 | 反向词表没有 品質→质量 |
| 同形异义 | 夜市賣的土豆很香。 | 夜市卖的**花生**很香。 | 土豆 | 台湾口语「土豆」=花生，词表没有语境判据 |

held-out 失误里同样有三类典型（词表基线的原理性局限，不是 bug）：
- **无分词**：方程式 → 方程序（`程式` 在词内部触发）；
- **缩写展开**：心房扑动 → 心心房撲動動（词典收了缩写「房扑→心房撲動」）；
- **守卫外溢**：数天后 → 數天后（identity 词条「天后」把别的语境里的 后→後 也挡住了）。

## 演进到 neural + 守卫（下一轮）

直接复用 `tools/build_yue_guard.py` 的对齐挖掘思路，把「允许替换集」搬到地区转换：

1. **平行语料**：普→粤用 vanderkorput 语料；地区转换可拉 OpenCC 词表 + 大陆/台湾
   双语平行文本（维基百科 zh-cn/zh-tw 双版本、两岸词汇对照表、moedict 数据）。
2. **对齐挖掘**：同长句对逐位对齐统计 `char_pairs` / 带邻接语境的 `left/right` /
   片段级 `word_pairs`（互选 + 频次 + 否定词过滤），产出 `tw_guard.marshal`。
3. **neural 解码约束**：seq2seq（参照 `experiments/train_yue_seq2seq.py`）输出时
   只允许有实证的替换（词表 ∪ 对齐），没有实证的改法回退词表基线——
   把本目录的歧义报告作为解码时的冲突检查器。
4. **语境判据**：失败模式表里的 程序/质量/土豆 一词多义问题，词表永远解不了，
   正是 neural + 语境守卫的价值所在；先用本目录的 16 句语境测试句当考卷。

## 已知局限

- 无分词，最长匹配会被词内子串骗到（方程式→方程序）；
- 词表覆盖缺口直接漏转（质量→品質、地铁→捷運），反向缺口更多（tw→cn 仅 1172 对）；
- 一对多目标只取首选，`視訊` 方向几乎不可达（被 影片 收敛）；
- `data/opencc_pairs.json` 3.38MB，入库需按 st_phrases 裁剪精简版。
